# BT-10 — Специфицировать модуль ANIMAL, подгруппа INV

## Текущее состояние

Инвентаризация поголовья места содержания через RFID/UHF-сканирование —
local-first черновик (пишется в БД на каждый скан, не только при завершении),
продолжаемый позже, с последующей офлайн-отправкой на сервер при
синхронизации. Технически это третий тип общего визарда «проход»
(`lib/pages/scanning/`), разделяемого с недостижимыми из UI типами
«выход»/«вход» — в реальной навигации приложения запускается только тип
`inventory`. Данные хранятся не в специализированной таблице, а в двух общих
Drift-таблицах (`UnsentReportAnimals`/`ReportAnimals`), разделяемых с этими же
недостижимыми типами. Сопоставление отсканированного номера с животным
происходит только на клиенте, в момент отображения — на уровне БД связи между
записью скана и животным нет вообще.

## Что делать

Последняя под-область модуля [MOD-4](../../2-specs/modules/MOD-4-ANIMAL.md)
(ANIMAL) — поверх уже заведённых
[ACTOR-5](../../2-specs/actors/ACTOR-5-USER-IN-ANIMAL.md)/
[ACTOR-4](../../2-specs/actors/ACTOR-4-SYSTEM-IN-SYSTEM.md), новая сущность
InventoryScanReport. Написать глоссарий (сущность, события) и use-case на
каждый достижимый сценарий по `R44`–`R49`, **включая read-экраны** (хаб
неотправленных сессий, итоговый отчёт, экспорт в Excel/PDF) — read-экраны не
откладываются, специфицируются в этом же проходе.

После этой под-области модуль `MOD-4-ANIMAL` специфицирован целиком по всем
семи под-областям (REG/MOVE/VAC/WEIGH/DISP/REPRO/INV).
