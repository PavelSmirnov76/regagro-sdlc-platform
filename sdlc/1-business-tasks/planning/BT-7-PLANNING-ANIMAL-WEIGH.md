# BT-7 — Специфицировать модуль ANIMAL, подгруппа WEIGH

## Текущее состояние

Фиксация веса одного или нескольких животных подряд (вручную либо через подключаемые по Bluetooth весы), с отметкой состояния здоровья — local-first, без немедленной отправки на сервер. Редактирование — тот же экран, автоматически переходящий в режим правки, если у животного уже есть взвешивание за сегодня (не только по явному переходу из хаба неотправленных). Модель синхронизации существенно проще, чем у VAC/MOVE: только один флаг `sync`, без отдельных `createdAt`/`updatedAt`/`deletedAt` — новая запись и отредактированная уже отправленная запись неразличимы локально, обе просто `sync: false`.

## Что делать

Продолжение модуля [MOD-4](../../2-specs/modules/MOD-4-ANIMAL.md) (ANIMAL) — новая под-область поверх уже заведённых [ACTOR-5](../../2-specs/actors/ACTOR-5-USER-IN-ANIMAL.md)/[ACTOR-4](../../2-specs/actors/ACTOR-4-SYSTEM-IN-SYSTEM.md), новая сущность AnimalWeighing. Написать глоссарий (сущность, события) и use-case на каждый достижимый сценарий по `R30`–`R34`, **включая read-экраны** (история взвешиваний животного, хаб неотправленных «В работе», посуточный отчёт по месту) — read-экраны не откладываются, специфицируются в этом же проходе (см. `SDLC-REWRITE-PLAN.md`, раздел VAC, и память `feedback_specs_dont_narrow_scope_silently`). Недостижимый из UI путь (удаление/повторная отправка уже синхронизированного взвешивания через `deleteImmediate`/`singleEditAnimalWeighingToAPI`/`singleSendAnimalWeighingToAPI`, экран без загрузки через `initWithoutLoad`) зафиксировать как находку в сущности, не выдавать отдельный use-case id.

## Открытые вопросы

Нет — но стоит отдельно отметить (не блокирует этот проход): batch-push (`storeAnimalWeighingsToSHTP`) отправляет все ещё не синхронизированные записи через эндпоинт **создания** (`weighing-event`), без id/remoteId в теле запроса — включая записи, которые локально являются правкой уже синхронизированного взвешивания (`saveEditedWeighing` просто ставит `sync: false`, сохраняя `remoteId`, но remoteId в payload push'а не попадает). Похоже на дубликат записи на сервере при правке уже отправленного взвешивания с последующим полным sync-проходом — тот же класс проблемы, что найден у VAC, но по другому механизму (там — дубликат из-за необновлённого `sync`-флага после успешного PUT; здесь — из-за того, что push вообще не различает create/update на уровне протокола). Зафиксировать в сущности и/или use-case пуша, не как отдельную задачу.
