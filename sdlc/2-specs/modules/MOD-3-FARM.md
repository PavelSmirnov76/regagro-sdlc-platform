# MOD-3 — FARM

`DataUpdateBloc._syncAuthData` вызывает синхронизацию мест и ферм безусловно, одно за другим, на каждом полном sync-проходе для авторизованного пользователя — синхронизация FARM ничем не гейтится.

`FarmRepository.storeFarmsOnRDS`/`updateFarmsOnRDS` отправляют фермы на сервер по одной, в цикле — каждая ферма отдельным HTTP-запросом, не батчем.

## Назначение

Справочник ферм (юридических площадок СХТП) и отделений (мест содержания животных внутри фермы) — создание/редактирование локально, с явной синхронизацией на сервер отдельным шагом. Удаление — только для отделений (при отсутствии закреплённых животных); удаления фермы как функциональности в продукте нет.

## Граница — что модуль explicitly не владеет

- Само животное (`Animal`) и его `farmId`/`placeId` — модуль ANIMAL (будет специфицирован позже). FARM лишь предоставляет id, на которые эти поля ссылаются, и каскадно переписывает их при замене локального id фермы/места на серверный — сам каскад будет описан в спеке ANIMAL, как часть use-case, который он завершает.
- Адресный справочник (страна/регион/район/населённый пункт/улица) — `Farm` хранит их как id-поля, сам справочник не специфицируется в этом модуле.
- Явный полный sync pass как таковой (`DataUpdateStartAll`, проверка сети до начала аплоада) — оркестратор, специфицируется модулем `SYSTEM` (последний в очереди), не здесь.
- Настройка видимости видов животных на шаге создания первой фермы — данные о видах принадлежат `HANDBOOKS` ([ENT-3](../entities/ENT-3-TAXONOMY-IN-HANDBOOKS.md)), сам факт локального выбора при создании фермы будет описан как часть use-case создания фермы в этом модуле, но не переопределяет владение сущностью.

`R3`/`R4`/`R10` (карточка фермы со статистикой, переключение между фермами,
карточка места) изначально были отложены как известный пробел — pure-read
требования без выделенного create/update/delete-события. Закрыты отдельным
проходом (`EVT-102`/`EVT-103`, `UC-205`…`UC-208`), тем же способом, что и
аналогичные read-экраны других под-областей `ANIMAL`.
