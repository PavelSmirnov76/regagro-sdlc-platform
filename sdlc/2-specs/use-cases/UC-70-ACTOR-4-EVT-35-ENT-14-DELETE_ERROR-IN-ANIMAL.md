# UC-70 — Sync push удаления вакцинации отказывает технически — исключение или ответ с непустым `errors` перехватывается внутри `_deleteVaccinationFromApi`, sync-проход безусловно продолжается к update-шагу

| | |
|---|---|
| Актор | [ACTOR-4](../actors/ACTOR-4-SYSTEM-IN-SYSTEM.md) |
| Событие | [EVT-35](../events/EVT-35-VACCINATION-DELETION-PUSH-SYNCED-IN-ANIMAL.md) |
| Сущность | [ENT-14](../entities/ENT-14-VACCINATION-IN-ANIMAL.md) |
| Результат | `DELETE_ERROR` |
| Модуль | [MOD-4](../modules/MOD-4-ANIMAL.md) |

## Назначение

Тот же sync-шаг, что описан в [EVT-35](../events/EVT-35-VACCINATION-DELETION-PUSH-SYNCED-IN-ANIMAL.md) — `VaccinationsRepository._deleteVaccinationFromApi` отправляет одним батч-запросом все ещё не отправленные строки [ENT-14](../entities/ENT-14-VACCINATION-IN-ANIMAL.md), локально помеченные к удалению. Здесь сам сетевой вызов заканчивается технически — либо `rpcClientSHTP.call` бросает исключение, либо ответ приходит нормально, но с непустым полем `errors`, и код сам бросает `Exception` в ответ на это. Оба случая перехватываются одним и тем же `catch` внутри `_deleteVaccinationFromApi`, который только логирует через `Talker.info` и не пробрасывает исключение дальше — `syncVaccinations` безусловно продолжает к update- и create-шагам того же прохода. В отличие от push перемещений ([UC-61](UC-61-ACTOR-4-EVT-30-ENT-13-CREATE_ERROR-IN-ANIMAL.md)) и удаления мест ([UC-42](UC-42-ACTOR-4-EVT-20-ENT-10-DELETE_ERROR-IN-FARM.md)), здесь нет вообще никакого локального эффекта ни на успехе, ни на отказе этого конкретного метода — строка, помеченная к удалению, просто не трогается в обоих случаях.

## Пользователь

[ACTOR-4](../actors/ACTOR-4-SYSTEM-IN-SYSTEM.md) — система, действующая во время уже запущенного пользователем полного sync-прохода (`DataUpdateBloc.on<DataUpdateStartAll>`), без участия человека в момент именно этого сетевого вызова. Сам проход запускается раньше диспатчем `DataUpdateStartAll` из `lib/pages/main/main_page.dart`, `lib/pages/profile/presentation/profile_page.dart`, `lib/pages/profile/presentation/widgets/profile_settings/profile_settings_view.dart`, `lib/pages/in_work/in_work_page.dart` или `lib/pages/data_update/data_update_page.dart`.

Предпосылка сценария — существование хотя бы одной уже синхронизированной строки [ENT-14](../entities/ENT-14-VACCINATION-IN-ANIMAL.md), локально помеченной к удалению (`deletedAt != null`, `updatedAt == null`, `createdAt == null`, `sync == false`, `shtpId` задан). Единственный код, устанавливающий такую пометку — `VaccinationsRepository.markVaccinationForDeletion` → `VaccinationsDao.markVaccinationForDeletion` — вызывается только из `VaccinationCardPage` (`lib/pages/vaccination_card/vaccination_card_page.dart`, строка с вызовом `.markVaccinationForDeletion(vaccination.id)`). Маршрут `Routes.vaccinationCard` нигде в `lib/`, кроме своей собственной регистрации и чтения `extra`-аргумента внутри самой страницы, не встречается как цель навигации (`grep -rn "Routes.vaccinationCard" lib/` не находит ни одного `pushNamed2`/`go`) — то есть ни один живой пользователь сегодня не может создать эту предпосылку через UI приложения. На практике сценарий воспроизводится только тестом, вставляющим строку с этими полями прямо в БД (см. «Связанные тесты»).

## CURRENT

### Основной поток

1. Полный sync-проход уже идёт: `DataUpdateBloc._syncAllData` последовательно вызывает `_movementReportRepository.syncMovements()`, `_disposalRepository.syncDisposals()`, `_syncEditedAnimals()`, `loadAnimals(event, emit)`, и, **последним** шагом всего метода, `await _vaccinationsRepository.syncVaccinations(true)` — позиционный аргумент `true` (`isFullSync`), `isDeleteErrors` не передан и остаётся дефолтным `false`.
2. Внутри `syncVaccinations(true)`: ветка `if (isFullSync)` выполняет по фиксированному порядку `await _deleteVaccinationFromApi()` → `await _updateVaccinationFromApi()` → `await _sendVaccinationsToApi()` — delete-шаг первый.
3. `_deleteVaccinationFromApi`: `vaccinations = await getDeletableVaccinationsWithDetails()` — `VaccinationsDao`-запрос с фильтром `sync == false && deletedAt != null && updatedAt == null && createdAt == null`, дополнительно требующий существующего животного (`if (animalWithDetails != null)` внутри цикла построения результата — строка без найденного `Animal` молча исключается из результата, см. «Альтернативные потоки»). В этом сценарии список непуст (иначе метод возвращается сразу — не этот сценарий).
4. Строится единственный запрос: `ApiMessage(link: '${Constants.registrationServiceApi}/vaccination-group-actions', method: ApiMethod.delete, headers: {"Accept-Language": LanguageService.locale}, data: {'ids': vaccinations.map((e) => e.shtpId).toList()})` — все `shtpId` отобранных строк одним списком.
5. `final response = await rpcClientSHTP.call(message)` — `rpcClientSHTP = getIt.get<ApiClient>(instanceName: 'farm_rpc')`, реальная реализация — `CustomDioClient`, оборачивающая `DioClient`.
6. Этот вызов технически заканчивается одним из двух путей:
   - `CustomDioClient.call` перехватывает исключение из `dio.request(...)` (сеть недоступна, таймаут, либо любой не-2xx статус — `DioClient` не переопределяет `validateStatus`, поэтому Dio по умолчанию бросает `DioException` вне диапазона 200-299), логирует его через собственный `Talker.error` и безусловно `rethrow` — исключение всплывает прямо в `_deleteVaccinationFromApi`.
   - Либо вызов возвращает обычный ответ (например, HTTP 2xx с телом, содержащим непустой `errors`), и уже в самом `_deleteVaccinationFromApi` условие `((response['errors'] ?? {}) as Map).isNotEmpty` истинно — код сам бросает `Exception(response['errors'])`.
7. Оба пути заканчиваются в одном и том же `catch (e, st)` внутри `_deleteVaccinationFromApi`: `getIt<Talker>().info('deleteVaccinationFromApi Error: $e st: $st')` — **уровень `.info`, не `.error`**, при этом это единственный и полный обработчик: нет `rethrow`, нет какого-либо изменения состояния, нет обращения к БД. Метод завершается нормально (`Future<void>`, без исключения).
8. Поскольку никакое исключение не всплывает наружу, `syncVaccinations` безусловно продолжает: `await _updateVaccinationFromApi()` (тот же паттерн — свой batch PUT, свой `catch` без `rethrow`) и `await _sendVaccinationsToApi()` (create-шаг; в предпосылке этого сценария нет ни одной ещё не отправленной новой вакцинации, поэтому `getNotSyncVaccinationsWithDetails()` возвращает пустой список и метод сразу возвращается, `if (vaccinations.isEmpty) return;`).
9. `syncVaccinations` вычисляет `vaccinationsWithErrors = await _getNotSyncVaccinations()` — `VaccinationsDao.getNotSyncVaccinations()`, единственное условие `sync == false`, без разбора на «новая»/«правка»/«удаление». Строка, помеченная к удалению на шаге 3, за шаги 2-8 не была тронута ни разу, поэтому по-прежнему `sync == false` — она попадает в этот снимок.
10. `await dao.clear()` — `BaseDao.clear()`, удаляет **вообще все** строки таблицы `Vaccinations`, без фильтра по `sync`.
11. `await _getVaccinationsFromApi()` — pull-шаг: постраничный `GET .../vaccinations`, каждая строка ответа вставляется через `insert(vaccination.toCompanion())` — `toCompanion()` не задаёт `id` (только `shtpId: Value(id-с-сервера)`), поэтому каждая пришедшая строка получает новый автоинкрементный локальный `id`.
12. `if (!isDeleteErrors) dao.insAll(vaccinationsWithErrors);` — поскольку вызывающий код (`DataUpdateBloc._syncAllData`) не передавал `isDeleteErrors`, используется дефолт `false`, ветка выполняется: `BaseDao.insAll` (`mode: InsertMode.insertOrReplace`) реинсертит снимок из шага 9 **с исходными локальными `id`** — строка, помеченная к удалению, возвращается в таблицу в точности такой же, какой была на шаге 3 (`deletedAt` то же, `sync == false`, тот же `id`).
13. `syncVaccinations` возвращается нормально; `_syncAllData`, `updateAndSyncRegagro`, `_syncAuthData` возвращаются нормально; `DataUpdateBloc.on<DataUpdateStartAll>` не входит в свой `catch` — эмитится `DataUpdateSuccess(resetNavigationOnSuccess: event.resetNavigationOnSuccess)`. Весь полный sync-проход репортится пользователю как успешный, несмотря на то что удаление этой вакцинации на сервере не подтверждено.

### Альтернативные потоки

- **Пустой батч.** Если `getDeletableVaccinationsWithDetails()` возвращает пустой список (нет ни одной строки с `deletedAt != null && sync == false`), `_deleteVaccinationFromApi` возвращается сразу после первой проверки (`if (vaccinations.isEmpty) return;`), сетевой вызов не выполняется вовсе — не этот сценарий.
- **Помеченная к удалению строка ссылается на животное, которого нет в БД.** `getDeletableVaccinationsWithDetails()` строит `VaccinationWithDetails` только внутри `if (animalWithDetails != null)` — если для `vaccination.animalId` нет соответствующей записи [ENT-11](../entities/ENT-11-ANIMAL-IN-ANIMAL.md), эта конкретная строка молча исключается из результата и, следовательно, из батч-запроса (не отправляется вообще, без ошибки). При этом `getNotSyncVaccinations()` (шаг 9) не делает join с `Animal` и всё равно её вернёт — строка так же реинсертируется на шаге 12, неотличимо от строки, которая была отправлена, но получила ошибку.
- **Два технических подтипа отказа объединены в один и тот же результат.** Брошенное `rpcClientSHTP.call` исключение (транспорт) и явный непустой `errors` в нормально дошедшем ответе (осознанный отказ сервера) обрабатываются кодом абсолютно одинаково — оба порождают `Exception`, пойманный одним и тем же `catch`. Это тот же паттерн объединения, что уже задокументирован для перемещений ([UC-61](UC-61-ACTOR-4-EVT-30-ENT-13-CREATE_ERROR-IN-ANIMAL.md)) и мест ([UC-42](UC-42-ACTOR-4-EVT-20-ENT-10-DELETE_ERROR-IN-FARM.md)): `DELETE_REJECTED` для push удаления вакцинации структурно недостижим — оба подтипа всегда дают `DELETE_ERROR`.
- **OK-исход того же события — не входит в этот сценарий.** Если `rpcClientSHTP.call` не бросает и `errors` пуст, `_deleteVaccinationFromApi` тоже просто возвращается нормально — код метода не содержит никакой отдельной success-ветки (нет вызова `deleteById`/`removeFromUnsyncList`/иного изменения строки) ни при успехе, ни при отказе. Наблюдаемая разница между OK и ERROR на уровне этого метода — только содержимое лога `Talker`, который в обоих случаях не виден пользователю. Соответствующий `DELETE_OK` use-case для [EVT-35](../events/EVT-35-VACCINATION-DELETION-PUSH-SYNCED-IN-ANIMAL.md) не входит в объём этого документа.

### Связанные сущности

- [ENT-14](../entities/ENT-14-VACCINATION-IN-ANIMAL.md) (Vaccination) — основная сущность сценария. Строка, помеченная к удалению, не изменяется ни на шаге 3-7 (сам отказавший запрос), ни на шаге 12 (реинсерт после `clear()`+pull) — она проходит sync-проход неизменной, с тем же `id`, `deletedAt`, `sync == false`.
- [ENT-11](../entities/ENT-11-ANIMAL-IN-ANIMAL.md) (Animal) — читается только как join-условие в `getDeletableVaccinationsWithDetails()` (строка без найденного животного молча исключается из батча, см. «Альтернативные потоки»); этим шагом не пишется.
- `DataUpdates` (журнал sync-прохода, специфицируется будущим модулем SYSTEM) — **не получает ни одной новой строки для этого отказа.** В отличие от push перемещений ([UC-61](UC-61-ACTOR-4-EVT-30-ENT-13-CREATE_ERROR-IN-ANIMAL.md), где исключение долетает до `DataUpdateBloc._emitError`/`_addDataUpdateError`), здесь исключение перехватывается и гасится внутри самого репозитория, на много уровней ниже — `DataUpdateBloc` вообще не узнаёт, что этот шаг отказал.

### Бизнес-правила

- Delete-push — единый батч-запрос на весь набор `shtpId` подходящих строк сразу, не по одной, как и update/create-push той же сущности ([ENT-14](../entities/ENT-14-VACCINATION-IN-ANIMAL.md), «Инварианты»). Но, в отличие от аналогичных batch-удалений ферм/мест ([UC-41](UC-41-ACTOR-4-EVT-20-ENT-10-DELETE_OK-IN-FARM.md)/[UC-42](UC-42-ACTOR-4-EVT-20-ENT-10-DELETE_ERROR-IN-FARM.md)), успех этого батча тоже не производит никакого локального удаления — семантика «батч успел/не успел» здесь не имеет наблюдаемого локального следствия вовсе.
- Логирование отказа — уровень `Talker.info`, не `Talker.error`, хотя это единственная точка обработки настоящей технической ошибки на этом шаге; ни `emit`, ни любое другое состояние `DataUpdateBloc`/`VaccinationsRepository` не меняется.
- Sync-проход продолжается безусловно к update-шагу (`_updateVaccinationFromApi`, тот же паттерн `catch` без `rethrow`) и к create-шагу (`_sendVaccinationsToApi`, в этом сценарии — no-op из-за пустого списка) независимо от исхода delete-шага; далее — к `_getNotSyncVaccinations()`/`dao.clear()`/`_getVaccinationsFromApi()`/`insAll()`, тоже безусловно.
- Результат — `DELETE_ERROR`, не `DELETE_REJECTED`, независимо от того, был ли конкретный отказ сетевым исключением или ответом сервера с непустым `errors` — оба варианта тонут в одном и том же молчаливом `catch`, не различаемом ни кодом, ни пользователем (см. «Альтернативные потоки»).

## Критерии приёмки

- Если для непустого батча `getDeletableVaccinationsWithDetails()` вызов `rpcClientSHTP.call` внутри `_deleteVaccinationFromApi` бросает исключение, либо возвращает ответ с непустым `errors`, метод логирует это через `Talker.info` и завершается нормально (`completes`, не `throwsA(...)`).
- `syncVaccinations(true)` после отказавшего delete-шага безусловно вызывает и update-, и create-шаг того же прохода — оба метода (`ApiMethod.put` и pull `ApiMethod.get`, дополнительно `ApiMethod.delete` самого отказавшего шага) фиксируются как реально вызванные через мок сетевого клиента.
- Ни одно поле строки, помеченной к удалению (`deletedAt`, `sync`, `updatedAt`, `createdAt`, `id`), не меняется этим отказавшим шагом: после завершения всего вызова `syncVaccinations(true)` в БД по-прежнему ровно одна такая строка, с тем же `deletedAt`, что и до попытки, и `sync == false`.
- Полный проход `DataUpdateStartAll`, частью которого является этот шаг, не видит это исключение вовсе: не порождает ни строки `DataUpdates`, ни `DataUpdateFailure` — весь проход при прочих успешных шагах завершается `DataUpdateSuccess`.

## Открытые вопросы и ограничения

- **Сценарий недостижим через живой UI сегодняшнего приложения.** Предпосылка (уже синхронизированная вакцинация, локально помеченная к удалению) может быть создана только вызовом `VaccinationsRepository.markVaccinationForDeletion`, единственный вызывающий — `VaccinationCardPage`, маршрут которой нигде не открывается ни с одного другого экрана (`grep -rn "Routes.vaccinationCard" lib/` не находит ни одного `pushNamed2`/`go` вне самой страницы). Весь механизм этого use-case полностью реализован и отдельно проверен репозиторным тестом (см. «Связанные тесты»), но на практике этот sync-шаг сегодня всегда обрабатывает пустой список — сценарий воспроизводим только тестом, вставляющим строку напрямую в БД.
- **У `_deleteVaccinationFromApi` нет никакого локального эффекта ни при успехе, ни при отказе.** В отличие от аналогичных delete-push для мест ([UC-41](UC-41-ACTOR-4-EVT-20-ENT-10-DELETE_OK-IN-FARM.md), успех вызывает `deleteAll`) или создания перемещений/животных (успех помечает `sync = true`), здесь метод не вызывает ни `deleteById`, ни `removeFromUnsyncList`, ни любое иное изменение строки ни в одной из веток — различие между OK и ERROR на этом шаге наблюдаемо только в содержимом лога `Talker`, который никуда, кроме внутреннего лога, не попадает.
- **Полное отсутствие сигнала об отказе где бы то ни было.** Ни `DataUpdates`, ни `DataUpdateFailure`, ни какой-либо UI-элемент не отражают этот отказ; лог — уровня `.info`, а не `.error`. Это даже более скрытный отказ, чем у push перемещений ([UC-61](UC-61-ACTOR-4-EVT-30-ENT-13-CREATE_ERROR-IN-ANIMAL.md)), где хотя бы весь sync-проход обрывается и пишется строка `DataUpdates` — здесь проход не только не обрывается, но и не оставляет вообще никакого следа неудачи вне лога.
- **Потенциальное дублирование строки при реальном (не тестовом) ответе pull-шага — не проверено эмпирически.** Поскольку DELETE в этом сценарии не подтверждён сервером, вакцинация по-прежнему существует на сервере; последующий безусловный `_getVaccinationsFromApi()` (тот же вызов `syncVaccinations`) в реальных условиях получил бы её снова через `GET .../vaccinations` и вставил бы **новой** строкой (новый автоинкрементный `id`, `sync: true`, `deletedAt: null`, тот же `shtpId`), в то время как `insAll(vaccinationsWithErrors)` следующей строкой реинсертирует **старую** строку (исходный `id`, `deletedAt` как было, `sync: false`, тот же `shtpId`) — итог: две локальные строки с одним и тем же `shtpId`. В существующем тесте это не проявляется, потому что мок `GET`-вызова всегда отвечает пустым `{'data': []}`, а не реальным списком, всё ещё содержащим эту вакцинацию — вывод сделан статическим чтением кода, не подтверждён отдельным тестом.
- **`DELETE_REJECTED` для этого события структурно недостижим**, тем же способом, что и для перемещений/мест: явный непустой `errors` в нормально дошедшем ответе и брошенное транспортное исключение обрабатываются одинаково, оба дают `DELETE_ERROR`.
- **Тест покрывает только транспортный вариант отказа** (`rpcClientSHTP.call` бросает `Exception`), не вариант «запрос дошёл, ответ содержит непустой `errors`» — оба ветвятся в один и тот же `catch`, но это разные условия в коде (см. «Основной поток», шаг 6); второй вариант не воспроизведён отдельным тестом.
- **Нет теста на уровне `DataUpdateBloc`.** Весь сценарий проверен только на уровне `VaccinationsRepository.syncVaccinations`, не как часть реального прохода `DataUpdateBloc.on<DataUpdateStartAll>` — утверждение «весь проход остаётся `DataUpdateSuccess`» в «Критериях приёмки» выведено из чтения кода (`_syncAllData` вызывает этот шаг последним, без собственного `try/catch`, а исключение здесь и не долетает до `_syncAllData` вовсе), а не подтверждено интеграционным тестом.
- **Гейт «должен существовать `Animal`» в `getDeletableVaccinationsWithDetails` не проверен тестом.** Если для `vaccination.animalId` нет строки в `Animals`, эта конкретная помеченная-к-удалению строка молча исключается из батча (не отправляется на сервер вовсе), но всё равно проходит через `getNotSyncVaccinations()`/`insAll()` неизменной — граница между «не отправлено на сервер» и «отправлено, но отказало» стирается уже на этапе выборки; не проверялось, является ли это осознанным поведением.
