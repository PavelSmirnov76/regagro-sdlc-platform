# ENT-11 — Animal

## Описание

Корневая сущность паспорта — Drift-таблица `Animals`. Общая для всех семи под-областей модуля [MOD-4](../modules/MOD-4-ANIMAL.md); здесь описаны только поля, относящиеся к регистрации/редактированию (REG) и разведению/родословной (REPRO) — поля, принадлежащие MOVE/VAC/WEIGH/DISP/INV, будут добавлены в этот же файл по мере специфицирования тех под-областей, не дублироваться отдельной сущностью. **REPRO не заводит отдельную сущность** — родители/потомки хранятся прямо на этой же таблице `Animals`, потомок вычисляется запросом (`motherId`/`fatherId` другого животного указывают на текущее), не хранится как обратная ссылка.

## Поля (актуальные для REG)

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | int, autoincrement | локальный id; `id < 0` = ещё не синхронизировано, `id >= 0` = синхронизировано — единственный признак, по которому различаются local-first и уже отправленные животные, отдельного статус-поля нет |
| `regagroId` | int? | серверный id (заполняется отдельно от `id`) |
| `farmId`/`placeId` | int? | ссылки на [ENT-9](ENT-9-FARM-IN-FARM.md)/[ENT-10](ENT-10-PLACE-IN-FARM.md) |
| `kindId` | int | обязательное, ссылка на [ENT-3](ENT-3-TAXONOMY-IN-HANDBOOKS.md) |
| `breedId`/`suitId` | int? | ссылки на [ENT-3](ENT-3-TAXONOMY-IN-HANDBOOKS.md) |
| `gender` | int | обязательное |
| `birthDate` | DateTime? | |
| `name` | text? | кличка |
| `number` | text? | приоритетный номер животного — заполняется из первого элемента списка идентификаций при регистрации, не обязательно из транспондера |
| `needsUpdate` | — | см. «Инварианты»: флаг отложенной sync-отправки правки |
| `errors` | text? | JSON с текстом серверных ошибок по полям, для показа под соответствующими полями формы редактирования |
| `userId` | int? | пользователь, создавший запись |
| `guid` | text? | клиентский идентификатор |
| `isMobile` | bool | признак мобильного (локального) создания |
| `disposalListId` | int? | принадлежит DISP, не описывается здесь |

Остальные поля таблицы (`ownerId`/`ownerEmail`/`ownerPhone`/`ownerName`, `address`/`latitude`/`longitude`, `birthDateFrom`/`birthDateTo`, `clinicName`, `nfcLink`, `isSuperGroup`, `animalPictures`, `source`) — не проверены в рамках этого прохода REG; будут описаны, когда/если реально используются под-областью, которая их читает.

## Поля (актуальные для REPRO)

| Поле | Тип | Комментарий |
|---|---|---|
| `motherId` | int? | ссылка на другую запись `Animal` (мать) — заполняется только если мать выбрана из уже зарегистрированных животных |
| `motherBirk` | text? | номер идентификации матери — заполняется всегда (и при выборе из списка, и при ручном вводе «не зарегистрировано»), независимо от того, задан ли `motherId` |
| `motherName` | text? | не используется этой под-областью для сохранения (`ReproductionCubit` всегда пишет сюда `null`) — присутствует в таблице, но выставляется, только если вообще выставляется, где-то за пределами найденного при этом проходе кода |
| `fatherId` | int? | симметрично `motherId`, отец |
| `fatherBirk` | text? | симметрично `motherBirk` |
| `fatherName` | text? | симметрично `motherName` — та же оговорка |

**Здесь не найдено отдельного `ENT` для «родителя, введённого вручную без привязки к записи» (R39, «не зарегистрировано»)** — это то же самое животное с `motherId`/`fatherId == null`, но заполненным `motherBirk`/`fatherBirk` (текстовый номер); различить «не зарегистрировано» от «зарегистрировано, но пока не найдено» на уровне схемы нельзя — оба случая имеют `motherId == null`.

## Инварианты

- **`id < 0` — единственный признак «ещё не синхронизировано».** Новый локальный id — `min(текущих отрицательных id) - 1`, гарантированно более отрицательный, чем все существующие локальные записи.
- **Замена локального id на серверный при успешной синхронизации обязана каскадно обновить все связанные локальные записи** (идентификации, и по мере специфицирования — взвешивания/вакцинации/перемещения/невыгруженное выбытие) **до** удаления исходной строки — распределённая по нескольким репозиториям операция, не одна БД-транзакция.
- **`needsUpdate` взводится только для уже синхронизированного животного** (`id >= 0`) при сохранении правки через `AnimalEditBloc` — локальное (`id < 0`) животное этот флаг не получает, так как оно и так целиком уйдёт на сервер при первой синхронизации. **Привязка родителя/потомка (REPRO) использует ровно тот же признак и ту же деферред-sync машинерию** (`ReproductionCubit.saveParent`/`saveChild` ставят `needsUpdate: true` по тому же условию `id >= 0`), не заводя собственного push/pull-события — отправка идёт тем же путём, что и обычная правка животного (см. [EVT-24](../events/EVT-24-ANIMAL-EDITED-DEFERRED-IN-ANIMAL.md)/[EVT-26](../events/EVT-26-ANIMAL-EDIT-SYNCED-IN-ANIMAL.md)).
- **Привязка потомка изменяет ЧУЖУЮ запись `Animal`, не ту, с чьего экрана инициировано действие.** `ReproductionCubit.saveChild` вызывается с экрана «Разведение» животного A, но обновляет `motherId`/`fatherId` выбранного животного B (потомка) — `needsUpdate` на B взводится по признаку `id >= 0` самого B, не A.
- **НАХОДКА — шаг «Родословная» в визарде регистрации мёртв.** `PedigreeStepPage`/`AnimalRegistrationEventChangePedigree` существуют в коде мастера регистрации, но `AnimalRegistrationBloc.currentSteps` (алиас `singleSteps`) никогда не включает `AnimalRegistrationStep.pedigree` — шаг не показывается ни при каком варианте визарда. Единственный достижимый способ привязать родителя/потомка — экран «Разведение» (`ReproductionCubit`) уже зарегистрированного животного, после регистрации.
- **НАХОДКА — `saveParent`/`saveChild` не сообщают пользователю об ошибке и застревают в `isLoading: true` при раннем `return`.** Оба метода логируют исключение через `Talker.error` без показа сообщения в UI; при этом если сработал охранный ранний `return` (не выбран родитель/потомок для сохранения) — `isLoading`, выставленный в начале метода, не сбрасывается обратно, состояние экрана остаётся «загрузка» бессрочно.
