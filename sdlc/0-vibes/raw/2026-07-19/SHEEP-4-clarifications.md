## Пункт 7 — RFID-считыватель: лейбл, регионы, и два найденных бага

Исследование (два фоновых прохода) показало, что переименование «Мощность»
→ «Дальность считывания» — чисто строковая правка одного ARB-ключа
(`power_range`) во всех локалях. Список частотных диапазонов
(`DeviceRegion`, 10 значений из SDK читалки GReader) сейчас подписан
техническими англоязычными строками без стран/регионов вообще
(`_regionLabels` в `region_selector_widget.dart`) — есть даже брошенный,
ни разу не использованный черновик локализации на 4 региона
(`rfid_region_selector__fcc/prc/eu/ru`), к которому эту задачу, похоже, уже
подступались раньше.

По ходу второго прохода (проверка «применяются после переподключения»)
найдены два реальных бага в передаче настроек на физическое устройство —
`ScannerService.applySettings()` вообще ничего не делает для всех типов
устройств, кроме TCD-терминала; реальная передача для остальных типов идёт
другими путями:

| Тип устройства | Диагноз |
|---|---|
| TCD-терминал | Применяется корректно при (пере)подключении |
| SMART-GATE BLE (`BluetoothGatesScannerDevice`) | Применяется корректно при (пере)подключении (`scan_gates_ble.dart`) |
| SMART-GATE TCP (`RfidTcpScannerDevice`) | **Баг**: регион передаётся через свитч, покрывающий только сохранённые индексы 0–3 → 4 аппаратных кода; любой индекс ≥4 (**включая дефолтный ETSI=4**) тихо схлопывается в код 0 (китайский диапазон) |
| RFID-04 TCP (`RfidGrpTcpScannerDevice`) | Тот же баг, что у SMART-GATE TCP |
| RFID-03 handheld (`RfidGrpBleScannerDevice`) | **Баг**: мощность/регион вообще никогда не передаются на устройство — UI показывает настройки, БД их хранит, аппаратно не применяются никак |
| A7 / UHF-стик (BT-клавиатурные донглы) | Не применимо — у этих устройств нет понятия мощности/региона вообще |

Уточняющие вопросы и ответы:

1. **Чинить баги в этом же проходе, вместе с текстом** — подтверждено.
2. **Список стран/регионов — покрываем полностью все 10 значений**, а не
   только 4 ключевых (см. выше — предположение об «только Россия» отклонено
   и признано необоснованным).
3. **Предупреждение «диапазон не для вашего региона» — не строим.**
   Помечено как отдельная задача, требующая обсуждения дизайна/формулировки,
   не в этом проходе.

Страны/регионы для всех 10 значений `DeviceRegion` взяты из общеизвестных
публичных регуляторных диапазонов UHF RFID (ETSI/FCC/национальные
регуляторы), сверенных по уже захардкоженным в коде частотам — не из
документации конкретного производителя (GReader), к которой доступа нет.
Отмечено как допущение для сверки продуктом/поставщиком железа при
необходимости.

## Пункт 9 — повторное взвешивание создаёт новую запись (массовое, не через карточку)

> Проблема в том, что повторное взвешивание одного и того же животного
> создаёт новую запись. Если сегодня уже было взвешивание, то нужно
> редактировать сегодняшнюю запись. Посмотри как это сделано в другом месте

Первый проход исследования показал, что дедуп «сегодняшней записи»
(`_findTodayWeighing`) уже реализован в `weigh_animal_cubit.dart`, причём
фикс уже в `develop` до даты этого тикета (подтверждено git-историей).
Постановщик уточнил: баг
реально воспроизводится, но не через карточку животного, а через
**массовое взвешивание**, и попросил перепроверить, вызывается ли
`_findTodayWeighing` действительно всегда, а не только в
одиночном сценарии.

Перепроверка нашла точную причину — она не в условии `if (animal != null)`
(это условие относится к обоим сценариям одинаково), а в том, **откуда
берётся сам объект `AnimalWithDetails`**:

- Одиночная карточка (`WeighAnimalCubit.initialize()`) грузит животное через
  `AnimalsRepository.getAnimalWithDetailsById` →
  `AnimalsDao.getAllAnimalsWithDetailsByFilters` (`animals_dao.dart:266-446`)
  — этот метод **явно подтягивает `animalWeighings`** (:400-401,432-434).
- Массовое взвешивание (сканирование/поиск по номеру,
  `WeighAnimalCubit.getAnimals()`/`searchByNumber()`/`tryGetAnimalByNumber()`)
  грузит животных через
  `AnimalsRepository.searchAllAnimalsWithDetailsByNumbersAndName` →
  `AnimalsDao._toListAnimalsWithDetails` (`animals_dao.dart:495-547`) — этот
  метод **не подтягивает `animalWeighings` вообще** (сравнение с методом
  выше — идентификации/виды/породы/масти/вакцинации есть, взвешиваний нет).

`_findTodayWeighing()` (`weigh_animal_cubit.dart:54-64`) начинается с
`if (weighings == null || weighings.isEmpty) return null;` — для животного,
загруженного через массовое взвешивание, `animalWeighings` всегда
`null`/пусто, значит `_findTodayWeighing` **всегда** возвращает `null`,
независимо от того, есть ли реально запись за сегодня в БД. В
`saveCurrentWeighingStayOnPage()` (:294-306) это даёт `id: ... ?? null ??
-1` → всегда `-1` → `saveWeighing()` всегда делает `insert`, никогда
`update`, для животных, найденных сканированием/поиском по номеру.

Фикс — в `AnimalsDao._toListAnimalsWithDetails`, подтянуть `animalWeighings`
тем же способом, что уже есть в `getAllAnimalsWithDetailsByFilters` (строки
400-401,432-434) — единая точка причины, единая точка фикса.

## Пункт 10 — аппаратный курок ТСД: быстрая проверка

Постановщик уточнил конкретный сценарий бага: устройство было настроено

запускаться). Попросил краткое исследование, без деталей — сам перепроверит
на реальном устройстве позже.

Быстрая проверка (не полный повторный аудит):
- Пустая/неготовая `buttonActionsMap` на старте (до первого
  `scanner/setButtonActions` от Dart) по умолчанию в нативном коде запускает
  **только UHF** (`MainActivity.java:3504-3508`,
  `if (buttonActionsMap == null || !containsKey) { triggerUhfScanner(); return; }`)
  — не QR. Эта гипотеза (гонка на старте) не объясняет находку.
- `_setButtonActionsToTerminal` (`scanner_service.dart:378-401`) всегда
  отправляет **полную** карту `{left, middle, right}` за один вызов, не
  частично — гипотеза «частичное обновление оставило QR от старого значения»
  тоже не подтверждается по коду.
- Дальше вглубь не копал по прямой просьбе («бегло, без деталей») — открытый
  вопрос, ждём проверки на реальном ТСД с логами.
