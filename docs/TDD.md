# TDD

Два контура разработки по TDD: сам MCP и задачи по коду приложения.

## 1. Разработка MCP (этот репозиторий)

Red → green → refactor. Тесты лежат в `mcp/tests/`, фикстуры — в `conftest.py`:

- **`mini_sdlc`** — крошечное, но валидное по закону дерево `sdlc/` во временной
  папке (PRD, BT, модуль, актор, сущность, событие, use-case + один захороненный
  модуль, чтобы проверять, что аллокация id считает `obsolete/`).
- **`service`** — `SdlcService`, привязанный к `mini_sdlc` + временная БД/транскрипт.

Цикл добавления фичи:

1. **Red.** Напиши тест на желаемое поведение (закон — в первую очередь). Примеры
   уже закрепляют инварианты: `test_update_is_supersede_not_inplace`,
   `test_entomb_moves_to_obsolete_with_header`,
   `test_allocate_counts_obsolete`, `test_every_mutation_is_audited`. Запусти —
   убедись, что падает по нужной причине.
2. **Green.** Минимальная реализация в `law/` (или `service.py`), пока тест не
   позеленел.
3. **Refactor.** Причеши, тесты остаются зелёными.

```bash
cd mcp
uv run pytest                     # весь набор
uv run pytest tests/test_prd.py   # один файл
uv run pytest -k entomb           # по имени
```

Правило: **никакой мутирующий метод сервиса не считается готовым без теста,
проверяющего, что он (а) соблюдает закон и (б) оставляет строку в аудите.**

## 2. Задачи по коду приложения (`agro_system`)

Ведутся по промпту `tdd_task`, который сервер отдаёт хосту. Суть — правило самого
проекта: после изменений в `lib/` обязателен `flutter test`.

1. **Red.** Сначала падающий `flutter test` на поведение из `Критерии приёмки`
   use-case'а. Привяжи тест к спеке: `group('UC-{id} — …')` — тогда связь
   восстанавливается `grep -r "UC-{id}" test/`, даже если прозаический список
   тестов в спеке устареет.
2. **Green.** Минимальная реализация, `flutter test` зелёный.
3. **Refactor.** Под конвенции проекта (тема/типографика, cubit/bloc, go_router,
   freezed), тесты зелёные.
4. **Результат** фиксируется в `sdlc/5-results/` (файл-зеркало задачи по имени):
   что сделано и что отложено.
5. **PR и сборка.** `open_pull_request`, затем при необходимости
   `build_and_deliver_apk`. Пока ключи не настроены — вызовы фейковые (безопасно),
   реальные включаются по `docs/SETUP.md`.

Задача не выполнена, если тесты не запускались после последнего изменения или падают.
